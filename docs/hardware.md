# UART and Tang Nano 9K milestone

## What we built, in plain language

Previously the engine was like a calculator with nobody connected to its keypad.
Our testbench could feed it numbers, but a real PC could not talk to it over USB.
Now there is a communication path around that calculator:

```
PC quote -> USB/UART bridge -> uart_rx -> packet_rx -> engine
PC reply <- USB/UART bridge <- uart_tx <- response formatter
```

1. **UART receiver:** watches a wire that normally stays high. A low start bit
   announces a byte. It samples eight data bits, then checks the high stop bit.
   A pair of registers synchronizes the incoming signal to our FPGA clock.
   A short false start is ignored; a bad stop bit is reported as a framing error.
2. **Packet parser:** assembles bytes into a quote. The `NQ` marker is the envelope
   label, the version is the form revision, and CRC is a calculated check for
   damaged contents. Fields may be assembled internally while arriving, but the
   engine cannot act until the complete candidate passes validation.
3. **Trading engine:** makes the same buy/sell/hold and risk decisions as before.
   Communication does not bypass the maximum-order, position, or kill rules.
4. **Response formatter and transmitter:** save the result into a reply packet
   and send its bytes back. The sequence number tells the PC which quote it answers.
5. **Board wrapper:** connects these pieces to the clock, reset button input, and
   serial pins. It holds reset during startup and synchronizes button release.

Stop-and-wait means the PC asks one question and waits for the complete answer.
This avoids needing a queue in the first hardware milestone. If you send another
complete quote while a reply is being transmitted, it is dropped, not postponed.

## Your PC: update and test before programming

From your existing clone:

```powershell
git pull --ff-only
python -m unittest discover -s tests -v
```

Use `py` instead of `python` if that is your Windows Python launcher. Core tests
need Python only. All HDL tests require `iverilog` and `vvp` on PATH; skipped HDL
tests are not evidence that your local simulation passed.

For the complete open-source toolchain, download and extract the Windows x64
[OSS CAD Suite](https://github.com/YosysHQ/oss-cad-suite-build/releases).
Activate its environment in each new PowerShell terminal, adjusting the path:

```powershell
. C:\tools\oss-cad-suite\environment.ps1
iverilog -V
vvp -V
yosys -V
python -m unittest discover -s tests -v
python tools/build.py
```

The environment adds both `bin` and `lib` to PATH. Adding only `bin` can cause
missing-DLL/system.vpi errors on Windows. This project was verified with the
20261019 suite. The script synthesizes, places, routes at 27 MHz, and packs
`build/nanoquant.fs`. It stops on command failure and does not program hardware.
Logs and timing JSON are in `build/`; build artifacts are ignored by Git.

## Gowin IDE alternative

Open `nanoquant.gprj`. It includes only synthesizable RTL, the pin constraints, and
the timing constraints; simulation testbenches must not be synthesis sources.
Select `nanoquant_top` as the top module. The supplied device is
`GW1NR-LV9QN88PC6/I5`, family `GW1NR-9C`, matching Sipeed's example. Check the device
marking on your actual board before building or programming.

Run synthesis and place-and-route, then inspect the timing report for the 27 MHz
clock. This IDE project is provided but was not tested in Gowin IDE here. A Gowin
build usually places its generated `.fs` in `impl/pnr/`; the open-source build
uses `build/nanoquant.fs`. Use the file generated by your chosen flow.

In Gowin Programmer, detect the board and use the SRAM programming mode for the
first trial. SRAM configuration is temporary and disappears when power is lost.
Programmer UI details, drivers, and successful hardware programming remain to be
checked on your FPGA PC. No physical board was connected during this development.

## Pin and clock sources

The mapping comes from Sipeed's official
[UART constraints](https://github.com/sipeed/TangNano-9K-example/blob/main/uart/src/top.cst)
and [device project](https://github.com/sipeed/TangNano-9K-example/blob/main/uart/uart.gprj):

| Signal | FPGA package pin | Use |
|---|---|---|
| clk | 52 | 27 MHz board oscillator |
| rst_n | 3 | Active-low reset input/button |
| uart_tx | 17 | FPGA output to onboard USB/UART bridge |
| uart_rx | 18 | FPGA input from onboard USB/UART bridge |

Sipeed documents the onboard UART bridge and 27 MHz clock in its
[UART tutorial](https://wiki.sipeed.com/hardware/zh/tang/Tang-Nano-9K/examples/lushaylabs/2_debugging_uart/debugging_uart.html).
Check your board revision against that wiring. The standard onboard bridge needs
no external UART jumper wires. CST numbers are FPGA package pins, not header
positions. The Gowin SDC times the 27 MHz clock and excludes the asynchronous input
paths into synchronizers. The open-source build instead supplies `--freq 27` to
nextpnr; it does not read the Gowin SDC. Synchronizer register-to-register paths
remain part of clock timing. No synchronous external data timing is claimed.

## Send quotes and compare actual board replies

On the PC connected to the programmed board:

```powershell
python -m pip install -r requirements-hardware.txt
python -m serial.tools.list_ports
```

Identify the board's serial COM port. Close terminal applications that might own
it. Press and release reset before every demo run, then substitute your port:

```powershell
python -m nanoquant.serial_demo --port COM5 --count 20 --seed 1 --kill-at-end
```

The tool sends a quote, waits for a reply, checks its CRC and sequence, compares
the order/position/kill state against Python, then sends the next quote. A mismatch
or timeout stops the run. Do not retry a timed-out request automatically: it could
already have changed the board's position. Reset the board before restarting.

The final two quotes exercise kill: the first latches kill, and the second confirms
that trading stays stopped. Reset is required to trade again.

`engine_cycles=1` reports the architectural register-stage count. The printed
`host_round_trip_us` is an actual host-clock measurement spanning send and receive;
it includes UART transfer, USB buffering, OS scheduling, and reply processing.
It is not engine latency. The 2 ms pause happens after that measurement.
No real board measurements have been collected yet.

## What is still outside this milestone

Physical-board acceptance, a dedicated emergency-stop input, duplicate detection,
queued/pipelined requests, explicit error replies, dashboard, and comparative
Python/C++/FPGA benchmarks remain future work. This is a simulated-order teaching
project. The transport intentionally makes no exactly-once delivery promise.
